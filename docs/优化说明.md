# JAX V-A Split Queue 与 VLM Batch 优化说明

本文记录当前 `jax-split-ipc` serving 路径中已落地的两项优化：请求入队回压，以及 VLM late FCFS batch 调度。重点说明设计原理，不展开性能数据和源码细节。

## 背景

JAX V-A split 将一次策略推理拆成 VLM prefix prefill 和 AE denoise 两段，并通过 IPC slab、lane credit 和进程间队列串联。高负载下，系统的主要排队通常发生在 VLM 请求队列侧；AE 本身较轻，但如果上游持续放入过多请求，VLM 会积累很长的队列等待，进而放大端到端延迟和尾部延迟。

此前的高压现象可以概括为两类：

- 在途请求数过大时，请求已经进入 runtime / VLM 队列，但尚未获得 prefix lane 或 VLM 计算机会，排队时间被堆到 `va_split_queue_wait` 和 `vlm_request_queue_wait` 中。
- FCFS 聚批在队头请求已经等待较久时仍倾向于凑大 batch。大 batch 有利于吞吐，但单次 VLM prefill 时间更长，会进一步增加已排队请求的等待。

优化目标不是简单增加 prefix slot，也不是把 VLM batch 一律调小，而是在延迟和吞吐之间做更稳健的 admission 与 batch 调度。

## 请求入队回压

runtime 侧新增了 request admission token。每个进入 `infer` / `infer_batch` 的请求在写入 VLM request queue 前，必须先拿到一个 admission token。token 总数默认跟 prefix slot 容量对齐，即 `max_prefix_slots`，当前默认仍是 `max_vlm_batch_size * 3`。

这个设计把系统的主要排队点从无界的 VLM request queue 前移到 runtime admission 层：

- 已进入 VLM 队列的请求数量被限制在 prefix slot 容量附近，避免队列无限增长。
- request queue 中的等待更接近真实可服务 backlog，而不是把过载请求提前塞进子进程。
- 当请求正常完成、worker 返回错误、worker shutdown，或父进程等待结果超时时，都会释放对应 admission token，避免回压自身漏票。

这条优化的核心作用是控制过载下的排队水位。它不会提高单次 VLM prefill 的计算速度，但能显著减少由过量 inflight 引入的尾部排队。

## VLM Late FCFS Batch 调度

VLM 进程仍保留 FCFS 聚批，但对「队头请求已经超过 FCFS 等待窗口」的情况加入 batch 上限收缩。当前目标 batch size 为 6。

调度规则如下：

- 正常情况下，VLM 仍按 `max_vlm_batch_size` 和可用 lane credit 形成 batch。
- 如果队头请求已经等待超过 `MAX_VLM_WAIT_MS`，且当前候选请求不足以立即填满原始 batch 上限，则将本次 batch limit 收缩到 6。
- 如果 backlog 已经足够深，可以立即形成满 batch，则不收缩，继续使用原始 batch 上限，避免高负载下吞吐损失过大。

这个规则针对的是「队头已经晚了，但 backlog 又没有深到必须追求满 batch」的区间。此时继续等待或凑到 B=8，会把 VLM prefill 单段时延和队头延迟一起拉高；适度降低 batch 上限，可以更快释放队头请求，同时保留一定的 batch 效率。

选择 6 而不是 4 或 7，是因为它在当前测试条件下更平衡：

- 4 能进一步降低单次 VLM prefill，但更容易牺牲高负载吞吐。
- 7 更接近原始满 batch，但对 VLM prefill 和 AE tail 的改善不稳定。
- 6 在降低 VLM prefill、稳定 AE tail 和维持吞吐之间更折中。

## 与 AE 稳定性的关系

AE 侧不是当前主瓶颈，但 AE 会受到 VLM 大 batch 和同卡 GPU 争用影响。VLM late batch 收缩后，AE 接收到 prefix 的节奏更均匀，单次 AE batch 规模也更可控，能降低 AE step 的 p95 抖动风险。

这不是通过限制 AE 并发实现的，而是通过减少上游 VLM 的长时间阻塞和批量突发，降低 AE 被动背压的概率。

## 设计边界

这两项优化都属于 admission / scheduling 层改动，不改变 IPC slab、lane credit 协议和模型计算图：

- 不增加 prefix slot 数量。
- 不改变 VLM / AE 模型函数。
- 不引入多 GPU。
- 不依赖硬 SM 配额。

因此它们适合先作为同卡 split serving 的稳定性和延迟控制基础。后续如果要继续提升高负载吞吐，重点仍应放在 VLM prefill 计算路径、输入 staging、编译形态和更细粒度的自适应调度上。

## 验证范围

当前代码配套了单元测试覆盖以下行为：

- admission token 会按 request id 释放，避免父进程侧回压漏票。
- late FCFS 且候选不足时，VLM batch 会收缩到目标上限。
- late FCFS 但候选已经足够填满 batch 时，VLM 仍保留满 batch。

实际 profile 验证使用同卡 `jax-split-ipc`、`SM=0/0`、`MAX_INFLIGHT=64`、`MAX_VLM_BATCH_SIZE=8`、`MAX_VLM_WAIT_MS=1.0`、`REQUEST_RATE_HZ_LIST=16,32`。测试过程中尽量选择当时最干净的单卡，但机器上仍存在其他常驻进程，因此 profile 数据只作为同机趋势参考。

# Two-tier Late FCFS 优化方案

## 现有 profile 的判断

在当前指定的 JAX profile 中，ours 还没有超过 baseline。轻载 `r8` 的吞吐基本打平，但 e2e p50 和 goodput 较差；`r16` 的吞吐也接近打平，但 median latency 明显受 VLM 排队和 batch wait 影响；`r32` 的吞吐低约 5-7%，并且 e2e 更差。

从 stage 分解看，拆分税主要不在 IPC 字节传输，也不在 prefix admission：

- `vlm_request_transfer + prefix_transfer + ae_result_transfer` 的 p50 合计大约只有 2-3ms。
- `prefix_admit_wait` p50 通常小于 0.5ms。
- `r16` 的主要可疑项是 `vlm_request_queue_wait` 约 28-32ms，以及 `vlm_batch_wait` 约 15ms。
- `r32` 的主要可疑项是 VLM under-batching：ours 的 `vlm_effective_batch_mean` 约 5.75，而 baseline 的 monolithic effective batch 约 7.5，导致 VLM prefill 效率和 request queue 都变差。

因此优化方向不应是继续明显加大 admission token 去喂满 AE。AE 在 `steps=5` 和中低负载下仍较轻，admission 等待也很小；扩大 admission 只会把更多请求提前压进 VLM 队列，放大 e2e p50 和 goodput 损失。当前更合理的目标是降低 VLM 路径上的排队和不必要等待，同时在真正过载时尽量恢复 VLM batch size。

## 方案一：two-tier late FCFS

当前已经实现的改动是将 late FCFS 拆成两层：

1. 普通 late：
   - 队头请求已经超过 `MAX_VLM_WAIT_MS`，但还没有深度超时。
   - batch limit 仍收缩到目标值 6。
   - feeder drain 只给一个短预算，目前是 4ms。

2. deep late：
   - 队头请求已经等待至少 `max(100ms, 4 * MAX_VLM_WAIT_MS)`。
   - 不再强制收缩到 6，允许回到原始 batch 上限。
   - feeder drain 使用原来的长预算，上限 25ms，用来尽量收满 batch。

这个规则的意图是把 `r16` 和 `r32` 分开处理：

- `r16` 主要优化 e2e p50 和 goodput。队头只是普通 late 时，不应为了多等 1-2 个请求而支付十几毫秒 batch wait。
- `r32` 已经明显过载，很多请求远超 SLO。此时 median 已经被大队列主导，更需要恢复 full batch 来提高 VLM 吞吐，避免 batch size 长期停在 5-6。

该改动只在 VLM 调度层生效，不改变 IPC slab、lane credit、prefix slot 的所有权和释放语义。

## 预期影响

预期指标变化如下：

- `e2e p50`：`r16` 应该下降，主要来自 `vlm_batch_wait_p50` 下降；`r8` 变化较小。
- `goodput`：`r16` 应该改善，因为 200ms SLO 附近的请求会少付一段 batch wait。
- `r32 throughput`：如果 deep-late 触发后 batch 能回到 7-8，吞吐 gap 应缩小；如果仍长期停在 B=6 左右，则说明瓶颈不只是 late cap，还需要更强的 queue-aware dispatch。
- `p95`：不是本轮主目标。deep-late 策略可能保留或放大部分尾部等待，但这是为高负载吞吐换取的取舍。

## 风险与调参点

主要风险是 deep-late 阈值和短 drain 预算需要实测校准：

- deep-late 阈值过高：`r32` 太晚才恢复 full batch，吞吐 gap 仍然存在。
- deep-late 阈值过低：`r16` 也容易走 full batch 路径，e2e p50 和 goodput 回退。
- short drain 过短：普通 late 下 batch 可能过小，VLM forward 效率变差。
- short drain 过长：又会回到 `vlm_batch_wait` 约 10ms 以上的问题。

当前取值偏保守：普通 late 用 4ms，deep late 用 100ms 下限。它的目标不是一次性大幅超过 baseline，而是先把 r16 的 median/goodput 税降下来，同时给 r32 留出恢复 batch 的通道。

## 后续备选优化

如果 two-tier late FCFS profile 后仍未追平 baseline，下一步按 ROI 建议如下：

1. queue-aware dispatch：
   - 当 backlog / candidate 已经达到目标 batch，立即发车，不继续按时间等。
   - 只有 candidate 不足且队头 age 满足条件时才继续 drain。
   - 目标是进一步减少 `vlm_batch_wait_p50`。

2. VLM 输入路径常数优化：
   - 减少 synthetic workload 中 prompt、image mask、sample kwargs 的重复转换。
   - 尽量让 parent 侧 batch envelope 复用已经构造好的结构。
   - 目标是压低 `vlm_input_stage + vlm_request_transfer` 的小常数收益。

3. r32 专用 full-batch 恢复策略：
   - 当 VLM request queue age 已经远超 SLO 时，优先吞吐而不是 median。
   - 可以考虑基于 head age 或最近 effective batch 的自适应 target batch。
   - 风险是低中负载误触发后损害 goodput。

# VLM 执行时间优化补充

## 背景

`03` 数据里，性能回退主要来自长 drain 过早介入：`steps=10` 的 `r32` 比 `02` 好一些，但 `r16` 被额外等待拖慢；`steps=5` 的 `r32` 在 B 接近 7.4 时，`vlm_prefix_forward_ms` p50 仍在 330ms 量级。也就是说，VLM 侧继续盲目追 B=8 会提高单批 forward 成本，并不一定改善 e2e p50/goodput。

## 本轮改动

1. 短 AE deep-late 目标从 B=8 调成 B=7。
   - 普通 late 仍维持 B=6。
   - `num_steps<=5` 且队头超过 deep-late 窗口时，慢 feeder 场景最多主动等到 B=7。
   - 如果 backlog 已经一次性有 8 个候选，仍允许 B=8，不破坏已有满 backlog 吞吐路径。

2. 长 AE 保持 B=6，并保留 500ms deep-late 门槛。
   - 目的仍是保护 `steps=10/r16` 的 e2e p50 和 goodput，避免像 `03` 那样过早进入长 drain。
   - `steps=10/r32` 已经严重过载时，长 drain 仍可帮助把实际 batch 拉回 B=6 左右。

3. VLM observation stack 增加单行 numpy 快路径。
   - 多个请求都是 shape[0]==1 的 numpy array 时，使用预分配 `np.empty` 逐行写入，再转成 JAX array。
   - 避免在 synthetic 单请求输入上重复构造临时 list + `np.concatenate`。
   - 该项只影响 `vlm_observation_stack_ms`，预期收益是几毫秒级，不会改变 IPC slab / lane credit 语义。

## 预期影响与风险

- `e2e p50`：`steps=5/r16` 和部分 `r32` 应下降，主要来自少吃 B=8 的 VLM forward 税，以及 observation stack 小幅下降。
- `goodput`：重点看 `r16`，应优先不低于 `02`。
- `r32 throughput`：可能比 B=8 deep-late 略降，但目标是用少量吞吐换 p50/goodput；若 throughput 明显掉到 `02` 以下，说明 B=7 太保守。
- 风险：如果真实瓶颈不是 VLM batch-size forward，而是 queue backlog 形成速度，B=7 只会减少 forward 单批耗时，不能单独解决 r32 throughput gap。

# Late FCFS hard-cap 验证与下一步优化

## 本轮结论

Parent 侧主动攒小 batch 的实测收益为负。即使把等待压到 0.5/1/2ms，`steps=5/r32` 仍出现 `vlm_batch_wait_p50=500.7ms`、`throughput=20.05/s`，明显差于 VLM 侧 batch。原因是 parent 等待改变了 VLM 到达形态，让 VLM 更容易缺料；它虽然能把单次 `vlm_prefix_forward_p50` 降到 139ms，但新增的排队/等待把收益吃掉。

因此本轮改成更保守的 VLM 侧 hard-cap：

- 普通 late：硬限制到 B=6。
- `num_steps<=5` 且 deep-late：硬限制到 B=7，即使 backlog 已经一次性有 8 个候选也不再发 B=8。
- `num_steps>5`：维持 B=6，保护 `steps=10` 的 median/goodput。
- IPC slab / lane credit 语义不变；只改变 VLM FCFS batch size 选择。

# Parent caller-flush 合包实验

## 实验动机

用户提出的 parent 合包不是“刻意攒到某个 batch 再发”，而是 parent 侧准备发送时，有多少已经排队的兼容请求就合多少。这样理论上可以让 VLM 侧一次拿到 B=2/3 的 batch envelope，减少 VLM 侧一个个 request 再拼 batch 的开销。

旧的 parent batching 版本使用后台 sender thread，`infer()` append 后 notify sender。实测负收益很明显，原因大概率是 sender 醒得过早，把原本 VLM 侧可以自然聚起来的请求拆散或改变到达节奏。

本轮改成 caller-flush：

- `infer()` append 到 parent pending queue。
- 只 `time.sleep(0)` 让出一次调度权，不设毫秒级等待，也不等目标 batch。
- 调用线程随后 flush 当前 pending 中兼容的请求。
- 如果自己的 request 已经被其他调用线程合进 batch，就不重复发送。
- JAX 和 PyTorch runtime 同步保持同构。
- IPC slab / lane credit 语义不变；该功能仍由 `JAX_VA_PARENT_BATCH=1` / `PYTORCH_VA_PARENT_BATCH=1` 或 `VA_SPLIT_PARENT_BATCH=1` 显式启用，默认路径不受影响。

## 结论

caller-flush parent 合包仍然不适合作为当前主优化：

- `steps=5/r16` goodput 从 hardcap 的 11.23 掉到 9.74，低于 baseline 10.73。
- `steps=5/r32` 虽然 goodput 数字略高，但 throughput 从 21.56/s 掉到 19.69/s，e2e p50 从 1368ms 恶化到 1955ms。
- r32 的 `vlm_input_stage_p50` 从 4.2ms 降到 0.05ms，说明 parent 合包确实减少了输入拼装常数。
- 但这点收益被 VLM 到达形态恶化吃掉：`vlm_request_queue_wait_p50` 从 586ms 升到 705ms，`vlm_batch_wait_p50` 从 3.9ms 升到 9.4ms，`vlm_effective_batch_mean` 从 6.61 降到 5.92。

因此目前不要启用 parent batching。它可以作为实验开关保留，但默认 benchmark 应继续使用 VLM 侧 hardcap。下一步更高 ROI 的方向仍是 VLM/AE 内部调度，而不是 parent 侧改变请求到达形态。

## 后续优化方向

1. VLM batch-size cost model。
   - 04 和 parent 实验都说明 B 稍大不一定更好：`steps=5/r16` 从 B≈2 提到 B≈2.2 时，VLM fwd p50 从 55ms 跳到 93ms。
   - 下一步应记录最近不同 batch size 的 VLM fwd EMA，在 late/head-age 场景下选择预计完成时间最短的 batch，而不是固定 B=6/7。

2. AE lane credit 返回与 active set 调度。
   - `steps=10` 的 split 输 baseline，除了 VLM queue，还有 AE 多步执行与 VLM 共享 GPU 的叠加。
   - 应继续检查 AE 是否能更早释放物理 prefix lane、减少 prefix active set 抖动，并避免 AE 在大 active batch 下把 VLM prefill 挤慢。

3. VLM input staging 只做局部快路径。
   - parent 合包证明 input staging 可以降，但全局到达形态代价更大。
   - 更稳的做法是在 VLM worker 内继续优化 `_stack_request_observations` / `_to_jax_tree` 的局部常数，不把合包提前到 parent。

## 下一步 ROI

1. 继续保留 hard-cap，停止默认启用 parent 主动等待 batcher。
   - parent batcher 只适合作为显式实验开关，不能作为默认优化。
   - 若继续试 parent batch，只允许“零等待、只合并已经同时排队”的模式。

2. VLM 路径下一步应做 queue-age aware dispatch，而不是更激进攒 batch。
   - 目标：当 head age 已经接近/超过 SLO 时，优先发 B6/B7；当 head age 很小且 backlog 已满时才允许更大 batch。
   - 预期影响：压 `r16` e2e p50/goodput，同时避免 `r32` throughput 明显掉。
   - 风险：阈值过低会牺牲 r32 throughput；阈值过高会回到 B8 forward 税。

3. `steps=10` 的主要空间不在 VLM forward，而在队列驻留和 AE 多步路径。
   - `hardcap s10/r32` 的 `AE step p50=27ms`、`VLM req q p50=598ms`，VLM fwd 约 262ms，继续只压 VLM batch size 不会追上 baseline。
   - 后续应看 AE denoise enqueue / complete block 与 result release 对 VLM credit 回流的影响。

# Parent zero-wait top-up 实验

## 实验目的

把 parent batching 改成“不主动等待”：parent 线程醒来时有多少已挂起的兼容请求就发多少；VLM 收到 parent batch 后继续从自己的 backlog/request queue 里 top-up 到当前 hard-cap 上限。这个设计避免 parent 为了攒 batch 增加显式等待，同时理论上能减少 VLM 侧一个个 stack 的常数开销。

实现仍保持 opt-in：

- JAX: `JAX_VA_PARENT_BATCH=1`
- PyTorch: `PYTORCH_VA_PARENT_BATCH=1`
- 共享开关：`VA_SPLIT_PARENT_BATCH=1`

IPC slab / lane credit 语义不变；新增的 per-row dequeue timing 只用于 profile 分解。

# Long-AE heavy-overload VLM batch target 实验

## 背景

`4090-ours-10-04` 显示 `steps=10` 的主要 gap 仍在 VLM 路径：

- `r16`: e2e p50 235.285ms，低于 baseline 200.116ms；VLM forward p50 100.736ms，VLM request queue p50 28.806ms。
- `r32`: e2e p50 1872.176ms，低于 baseline 1545.747ms；VLM forward p50 263.159ms，VLM request queue p50 604.762ms。

之前尝试过两类方向：

- parent batching / top-up：减少了局部 input staging，但改变请求到达节奏，实测负收益。
- online adaptive VLM batch cap：没有稳定触发关键过载点，`steps=5` 实测退化。

因此本轮删除这些没有确认提升空间的路径，避免 runtime 继续膨胀。当前不再保留 parent batching 实现和 adaptive EMA cap，只保留已验证更稳的 VLM 内部 hardcap / late-FCFS 逻辑。

## 改动

历史实验中曾加入一个很小的分支：当 `num_steps > 5` 且 head request 已经超过 long-AE deep-late 窗口时，late FCFS 的 VLM target batch 从 6 降到 5。普通 `steps=10` late 场景仍用 6；`steps<=5` 深度 late 仍可用 7。

目的：

- 不影响 `steps=5` 路径。
- 尽量不影响 `steps=10/r16` 的中载路径。
- 只在 `steps=10/r32` 这类已经严重排队的场景降低 VLM forward 曲线和 AE 大 batch step 开销。

JAX 与 PyTorch 当时同步实现，IPC slab / lane credit 语义不变。该分支现已删除，本节仅记录实验。

# AE batch cap / prefix slots 与 SM 利用判断

## 判据修正

当前目标应按同一个统计量跨所有 rate 判断，而不是不同 rate 用不同统计量拼接胜出。优先目标是：

- `E2E p50` 全 rate 优于 baseline。
- `goodput` 全 rate 优于 baseline。
- `E2E p95` 可作为次要指标，允许牺牲。

按这个判据，当前 ours 还没有达标；`r8/r16/r32` 没有任何一组同时让 `E2E p50` 和 `goodput` 全 rate 优于 baseline，更没有达到 20% 级提升。

## SM 利用判断

当前没有 Nsight counter 级证据，04 / AE cap profile 中 `gpu_sm_util_mean` 为空；以下是基于已有 stage/contention profile 的判断。

已有 `logs/tests/jax-contention-b1-20260811/profile.json` 和 `logs/tests/jax-contention-b8-20260811/profile.json` 显示：

|---:|---:|---:|---:|---:|---:|---:|
| 1 | 49.309 | 49.886 | 1.012x | 2.449 | 5.769 | 2.356x |
| 8 | 321.315 | 321.034 | 0.999x | 4.684 | 18.470 | 3.943x |

这说明在 0/0 MPS 并发下，AE 基本是在 VLM 的空隙或低优先级资源里跑；VLM forward 没有被 AE 明显拖慢。AE 自身会被显著拖慢，但 AE 不是主瓶颈。

已有 `logs/JAX/openpi_jax_stage_mps_profile/summary.json` 显示 VLM 对 SM quota 很敏感。例如：

| batch | sm20 VLM p50 | sm60 VLM p50 | sm80 VLM p50 | sm100 VLM p50 |
|---:|---:|---:|---:|---:|
| 1 | 135.932 | 51.536 | 43.728 | 40.167 |
| 8 | 942.585 | 317.477 | 248.867 | 217.613 |

所以不建议再用固定 SM quota 切给 AE；这会直接伤 VLM。更合理的方向是保持 0/0，让 AE 机会式执行，同时控制 AE batch 不要制造过长 step。

## 下一步 ROI 排序

1. SLO-aware / age-aware VLM admission：当 head request 已接近或超过 SLO 分界时，优先用较小 VLM batch 快速放行，而不是继续追求吞吐 batch。预期改善 `E2E p50` 和 `goodput`，代价是 `r32 throughput` 可能略降，p95 可能更差。

2. 动态 AE cap：默认维持较大 AE cap，检测 VLM queue 非空或 head age 超窗时临时把 AE cap 限到 6，队列恢复后放开。预期减少 `steps=10/r16/r32` 的 AE 干扰窗口，风险是状态机更复杂，且现有静态 cap6 已证明收益有限。

3. VLM forward 输入路径微优化：复查 batch assemble、tree slice、device_put / host copy 是否每批重复做不必要工作。预期只影响 `VLM fwd p50` 外的 staging 税，收益大概率是个位数 ms，不太可能单独带来 20%。

综合判断：单卡两进程拆分仍有真实并行，但当前利用方式不是“VLM 有大量可被 AE 免费填满的空 SM”。VLM 是主导 stage，AE 可重叠但会变慢；净收益上限薄，20% 级全 rate p50/goodput 提升需要明显改变队列策略，而不是继续静态调 batch。

# SLO-aware VLM rescue 负例

## 尝试内容

按“牺牲 p95、优先救 e2e p50/goodput”的目标，尝试在 VLM FCFS batching 中加入 queue-age based rescue：

- B1 rescue：当 head request 在 VLM queue 中等待超过 16ms，且候选请求数较少时，把 VLM batch 上限压到 1。
- B2-only rescue：删除 B1，只在候选请求数已有 2-3 个时，把 VLM batch 上限压到 2。

两版都保持 IPC slab / lane credit 语义不变，并同步实现过 JAX 与 PyTorch。实测后已从代码删除，因为没有正收益。

## 结果

- B2-only rescue：`logs/tests/jax-slo-rescue-b2-s10-r8r16-gpu0`

| B1 rescue | 8 | 6.680 | 123.139 | 7.084 | 49.761 | 0.000 | 1.030 |

## 结论

B1 rescue 能显著降低单次 VLM forward，但把服务率打穿了，r16 的 VLM request queue p50 从 aecap6 的 27.445ms 涨到 163.731ms，e2e p50/goodput 都明显变差。

B2-only rescue 避免了吞吐崩塌，但没有改善 r16 p50，goodput 还从 6.609 降到 6.182；r8 也没有收益。说明当前 r8/r16 的问题不是简单“late 时少凑 batch”能解决：B1/B2 降 forward 的收益会被服务率下降和 queue 重排抵消。

这条策略不保留。后续如果继续追 VLM 侧，应优先看更底层的 per-batch VLM execution/input staging，而不是按 queue age 动态压 batch。
