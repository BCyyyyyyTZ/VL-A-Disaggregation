# VLA 中 TTFA 及相关实时性指标调研

调研日期：2026-08-06

## 结论摘要

在 VLA（Vision-Language-Action）和机器人策略领域，类似 LLM 中 `TTFT`（Time To First Token）和 `TPOT`（Time Per Output Token）的统计量是有意义的，并且已经开始被明确提出。

最直接的术语是 `TTFA`，即 `Time To First Action`。它可以定义为：

> 从新观测、语言指令或推理请求进入策略系统，到第一个可执行动作被生成、下发或开始执行之间的时间。

截至目前，`TTFA` 不是传统机器人学习论文中长期统一使用的标准术语，但在 2026 年的 VLA 实时推理论文中已经被明确使用，尤其是 `FASTER: Rethinking Real-Time Flow VLAs`。更早的相关工作通常研究 `latency`、`inference delay`、`control frequency`、`replanning frequency`、`action chunking`、`execution horizon`、`reaction time` 等指标，而不是直接命名为 `TTFA`。

总体判断：

- `TTFA` 可以看作 VLA 中对应 LLM `TTFT` 的指标。
- 对 VLA 来说，`TTFA` 比 LLM 的 `TTFT` 更接近控制系统性能指标，因为它直接影响机器人对新环境状态的响应速度。
- VLA 中也存在类似 `TPOT` 的概念，但通常不叫 `TPOT`，而是表现为 `time per action`、`action emission interval`、`chunk generation latency`、`replanning frequency` 或 `control frequency`。
- 对 action chunking、diffusion/flow policy、异步推理、远程推理部署来说，单独报告总推理延迟并不够，`TTFA`、完整 chunk 延迟和有效反应时间都需要统计。

## TTFA 与 LLM 指标的类比

LLM 推理中常见指标：

- `TTFT`：用户请求到首个 token 输出的时间。
- `TPOT`：首 token 之后，每个输出 token 的平均生成时间。
- `E2E latency`：整个回答完成的端到端时间。
- `throughput`：单位时间处理 token 或请求的能力。

VLA/机器人策略中可以类比如下：

| LLM 指标 | VLA/机器人中的近似对应 |
| --- | --- |
| `TTFT` | `TTFA`，新观测到第一个新动作输出的时间 |
| `TPOT` | `Time Per Action`、动作 token 解码时间、action emission interval |
| 总生成延迟 | 完整 action chunk 生成时间 |
| token throughput | action throughput、replanning Hz、control Hz |
| KV/cache 延迟影响 | 视觉编码、动作解码、flow/diffusion sampling、网络传输、动作队列延迟 |

需要注意的是，VLA 的动作生成方式不一定是自回归 token-by-token。

对于 autoregressive VLA，例如将动作离散化为 token 输出的模型，`TPOT` 类比比较直接：每个动作 token 或每个动作维度的解码时间会影响动作生成速度。

对于 diffusion/flow/action chunking VLA，策略通常一次生成一段动作序列，瓶颈往往来自多步 denoising/flow sampling、视觉编码、动作 chunk 解码和系统调度。此时 `chunk latency`、`TTFA`、`replanning frequency` 比传统 `TPOT` 更有解释力。

## 为什么 TTFA 有意义

### 1. 影响机器人对动态环境的反应

机器人控制不是纯文本生成。LLM 首 token 慢主要影响用户体感；VLA 首动作慢会导致机器人继续执行旧动作，或者在新环境状态下迟迟不能采取动作。

在以下任务中，`TTFA` 会直接影响成功率：

- 抓取移动物体。
- 传送带分拣。
- 乒乓球、抛接等高速交互任务。
- 人机协作中的避让与接触控制。
- 动态障碍物环境中的导航或 manipulation。

### 2. 暴露 action chunking 的响应性代价

action chunking 可以减少推理频率，让机器人动作更平滑，但也会降低系统对新观测的响应速度。

典型权衡：

- chunk 越长，动作越平滑，推理压力越小。
- chunk 越长，机器人越长时间执行旧计划，对环境变化越不敏感。
- chunk 越短，响应更快，但可能出现动作不连续、mode jumping 或 jerk。

因此，在 action chunking VLA 中，仅报告平均推理延迟是不够的。需要同时报告：

- 新观测多久能影响第一个动作。
- 完整 chunk 生成需要多久。
- chunk 执行 horizon 多长。
- 策略多久重新规划一次。

### 3. 区分“机器人一直在动”和“机器人反应快”

异步执行可以让机器人持续执行已有动作，减少 chunk boundary 处的停顿。但这不等于对新观测反应快。

例如：

- 系统 A：持续执行旧 chunk，视觉观测更新后 300 ms 才生成新动作。
- 系统 B：可能每次只生成短 chunk，但 50 ms 内能让新观测影响动作。

两者的平均控制连续性可能都不错，但动态任务中的表现会明显不同。`TTFA` 正是用于衡量这种“新信息进入后多久能产生首个新动作”的延迟。

### 4. 适合系统部署和 profiling

VLA 部署常见瓶颈包括：

- 视觉 encoder。
- LLM/VLM backbone。
- 动作 head。
- diffusion/flow sampling steps。
- action chunk queue。
- 机器人控制器通信。
- server-client 网络延迟。
- GPU 调度和 batch。

`TTFA` 可以作为端到端系统指标，帮助判断优化是否真的改善了机器人实时反应，而不是只改善了离线吞吐。

## 相关论文与线索

### 直接提出或接近 TTFA 的工作

#### FASTER: Rethinking Real-Time Flow VLAs

- 作者：Yuxiang Lu et al.
- 时间：arXiv 2026
- 领域：VLA、flow policy、real-time robot control
- 链接：https://arxiv.org/abs/2603.19199

该论文是目前最直接讨论 `TTFA` 的工作。论文明确将 `TTFA` 类比为 LLM 中的 `TTFT`，指出标准 flow-based VLA 需要完成完整采样过程后才能输出动作，因此首动作延迟会成为实时控制瓶颈。

论文提出：

- `Time to First Action (TTFA)`。
- 将 VLA 反应时间拆解为首动作延迟和 execution horizon。
- `Horizon-Aware Schedule`。
- 流式 action generation pipeline。

它的核心观点是：现有异步推理方法主要缓解轨迹平滑性问题，但没有充分解决新观测到新动作之间的反应延迟。

#### Real-Time Execution of Action Chunking Flow Policies

- 作者：Kevin Black, Manuel Y. Galliker, Sergey Levine
- 会议：NeurIPS 2025
- 链接：https://arxiv.org/abs/2506.07339

该论文提出 Real-Time Chunking (`RTC`)，目标是在 action chunking flow policy 中处理推理延迟和异步执行问题。

相关点：

- 研究 action chunking policy 的 real-time execution。
- 关注 inference delay 下如何保持动作连续。
- 解决完整 chunk 推理较慢导致的控制停顿问题。
- 与 `TTFA` 高度相关，但重点更偏向异步执行和平滑动作，而不是显式定义首动作延迟指标。

#### Adaptive Action Chunking at Inference-time for Vision-Language-Action Models

- 作者：Yuanchang Liang et al.
- 会议：CVPR 2026
- 链接：https://arxiv.org/abs/2604.04161

该论文提出 Adaptive Action Chunking (`AAC`)，在推理时根据动作 entropy 自适应调整 chunk size。

相关点：

- 明确讨论 chunk size 与 responsiveness 的权衡。
- 大 chunk 提高稳定性和一致性，但降低反应速度。
- 小 chunk 提高响应性，但容易导致 mode jumping 或动作抖动。
- 虽不一定使用 `TTFA` 术语，但研究问题与 TTFA 的意义高度相关。

该论文关注 diffusion-based VLA 的实时推理，用 speculative inference 降低完整推理延迟。

相关点：

- 针对 diffusion VLA 的多步采样延迟。
- 报告了 full inference latency 和 speculative round latency。
- 适合作为研究 `TTFA`、chunk latency、实时响应性的系统优化参考。

## 其他相近但不同的研究方向

计算机视觉和视频理解中也有 `time to first action` 或类似表述，但含义不同。

例如：

#### Online Real-Time Multiple Spatiotemporal Action Localisation and Prediction

- 作者：Gurkirt Singh et al.
- 会议：ICCV 2017
- 链接：https://openaccess.thecvf.com/content_iccv_2017/html/Singh_Online_Real-Time_Multiple_ICCV_2017_paper.html

该方向研究在线动作检测、动作定位和 early action prediction。这里的 `first action` 往往指视频中动作第一次被检测或预测出来，而不是机器人策略生成的第一个可执行动作。

因此，这类论文可以作为“早期预测/在线检测”背景参考，但不应直接等同于 VLA 控制中的 `TTFA`。

## 建议在 VLA 系统中统计的指标

如果要在 VLA profiling 或实验报告中系统评估实时性，建议同时记录以下指标：

### 端到端反应指标

- `TTFA`：新观测进入系统到第一个新动作输出/下发/执行的时间。
- `Effective reaction latency`：环境变化发生后，到机器人实际执行受新观测影响的动作之间的时间。
- `Observation staleness`：当前执行动作所依赖的观测距离当前真实时间有多旧。

### 动作生成指标

- `Full chunk latency`：完整 action chunk 生成完成的时间。
- `Time per action`：平均每个动作的生成时间，适合自回归或逐动作解码策略。
- `Action token latency`：如果动作被 tokenized，可以统计动作 token 的 TTFT/TPOT。
- `Denoising/flow step latency`：diffusion/flow policy 中每一步采样的时间。

### 控制执行指标

- `Control frequency`：底层控制器实际执行频率。
- `Replanning frequency`：策略基于新观测重新规划的频率。
- `Execution horizon`：每个 chunk 实际执行多长时间。
- `Action queue length`：动作缓冲队列长度。
- `Chunk overlap / blending cost`：异步执行或 RTC 类方法中的 chunk 融合开销。

### 任务表现指标

- `Success rate under injected delay`：人为注入不同延迟下的成功率。
- `Success rate under moving target speed`：目标运动速度变化下的成功率。
- `Collision / safety violation rate`：延迟导致的安全问题。
- `Jerk / smoothness`：动作连续性和平滑性。
- `Recovery latency`：扰动发生后恢复到有效动作的时间。

## 一个可操作的 TTFA 定义

为了避免不同系统口径不一致，可以在实验中明确区分三个时间点：

- `t_obs`：新观测帧、状态或语言请求进入策略服务的时间。
- `t_action_ready`：第一个新动作在策略端生成完成的时间。
- `t_action_exec`：该动作被机器人控制器接收或实际开始执行的时间。

对应指标：

```text
TTFA_policy = t_action_ready - t_obs
TTFA_execution = t_action_exec - t_obs
Control_transfer_delay = t_action_exec - t_action_ready
```

如果系统是异步 action chunking，还应记录：

```text
Chunk_latency = t_chunk_ready - t_obs
Execution_horizon = chunk_size / control_frequency
Observation_staleness_at_exec = t_action_exec - t_obs_used_by_action
```

## 对当前课题的启发

如果研究 VLA disaggregation、VLM/Action Expert 分离、MPS、多进程推理或远程推理，`TTFA` 是一个很适合补充到 profiling 中的指标。

尤其需要关注：

- VLM 首阶段输出延迟是否决定 `TTFA`。
- Action Expert 是否可以在 VLM 完成前提前启动或流式接收中间表示。
- 分离式部署是否降低吞吐但增加首动作延迟。
- 异步执行是否只是保证机器人不停顿，而没有降低新观测到新动作的反应时间。
- batch、MPS、CUDA graph、JAX/PyTorch compile 是否改善平均吞吐但损害 tail latency。

建议报告时不要只给平均值，还应给：

- p50 / p90 / p95 / p99 `TTFA`。
- p50 / p90 / p95 / p99 `full chunk latency`。
- 首动作可执行时间线。
- 分模块耗时分解：vision encoder、VLM、AE/action head、IPC、网络、controller。
- 在不同 request rate 和 max inflight 下的 tail latency。



## 多机器人工厂场景下的 VLA 推理指标

在多机器人工厂场景中，常见部署方式是一张或几张 GPU 作为边缘算力节点，给若干机器人提供 VLA 推理服务。此时最重要的指标不只是平均 `E2E latency` 或裸 `throughput`，而是：

> 在多台机器人共享边缘 GPU 时，每台机器人能否稳定、低尾延迟、低过期率地拿到有效动作。

因此，系统评估应优先关注 `goodput under deadline`、尾延迟、动作新鲜度和任务成功率。

### 核心指标优先级

| 指标 | 定义 | 重要性 |
| --- | --- | --- |
| `TTFA` | 请求或观测进入系统到第一个可执行动作产生的时间 | 决定机器人对新环境的最快反应。动态任务中，它通常比完整 chunk latency 更关键 |
| `E2E latency` | 观测进入到完整动作 chunk 返回或动作被执行的端到端时间 | 衡量完整推理链路成本，但不能单独代表实时性 |
| `Goodput` | 单位时间内满足 deadline 和质量要求的有效请求数 | 多机器人共享 GPU 时比裸吞吐更关键。超时动作即使被生成，也可能没有控制价值 |
| `Deadline miss rate` | 超过控制截止时间的请求比例 | 工厂场景中，尾延迟会直接变成动作过期、停顿或安全风险 |
| `Action staleness` | 当前执行动作基于多久以前的观测 | 衡量机器人是不是在执行旧观测下的动作 |
| `Replanning Hz` | 每个机器人实际获得新策略输出的频率 | 决定闭环控制更新能力 |
| `TPA / Time Per Action` | 平均每个动作生成时间，或 chunk 内摊销时间 | 用来比较 action head、chunk size、batching 策略 |
| `Full chunk latency` | 完整 action chunk 生成时间 | 对 action chunking、diffusion/flow VLA 很关键 |
| `Queueing delay` | 请求等待 GPU 调度的时间 | 多机器人共享 GPU 时，排队延迟常常比模型计算本身更影响尾延迟 |
| `p95 / p99 latency` | `TTFA`、`E2E latency`、`queueing delay` 等指标的尾延迟 | 工业场景通常更怕偶发慢请求，而不是平均值略高 |

### 机器人实时反应层指标

这类指标最适合放在论文或系统评估的主表中：

```text
TTFA_policy = t_first_action_ready - t_obs_received
TTFA_exec = t_first_action_executed - t_obs_captured
Action_staleness = t_exec - t_obs_used
```

建议统计：

- `TTFA` 的 p50 / p90 / p95 / p99。
- `TTFA_exec` 的 p50 / p90 / p95 / p99。
- `Action staleness` 的 p95 / p99。
- `Deadline miss rate`。
- `Per-robot replanning Hz`。

原因是机器人真正关心的是“新观测多久能改变动作”。在多人、多机器人、移动物体、传送带等场景中，平均 `E2E latency` 很容易掩盖 p99 卡顿。

### 多机器人服务层指标

共享边缘 GPU 时，系统层指标应重点看：

- `Throughput`：系统每秒完成多少 VLA 推理请求。
- `Goodput`：系统每秒完成多少个在 deadline 内的有效请求。
- `Per-robot goodput`：每台机器人实际获得的有效推理频率。
- `Fairness`：不同机器人之间的 p95 / p99 `TTFA` 是否差距过大。
- `Admission failure rate`：系统拒绝、丢弃或降级请求的比例。
- `Queueing delay` 的 p50 / p95 / p99。
- `GPU utilization` 和 `memory utilization`。

这里 `goodput` 比 `throughput` 更重要。例如系统每秒能处理 100 个请求，但其中 40 个超过 200 ms 控制 deadline，那么有效产能不应按 100 计算，而更接近 60。

### 模型推理层指标

对 OpenPI、π0、GR00T 等 VLA 模型，可以将推理延迟拆成以下模块：

- `Vision encoder latency`。
- `Language / VLM backbone latency`。
- `Action expert / action head latency`。
- `Flow / diffusion sampling latency`。
- `Per denoising step latency`。
- `Full chunk latency`。
- `First action decode latency`。
- `TPA = full_chunk_latency / action_chunk_size`。

原因是 VLA 不是单一 LLM decode。尤其是 OpenPI / π0 风格的 flow 或 action chunking 模型，完整 chunk 可能较慢，但如果第一个可执行动作可以流式或提前生成，机器人仍可能具备较好的反应速度。

### 控制质量层指标

只看延迟和吞吐不够，还要看延迟下动作是否仍然可用：

- `Task success rate under load`。
- `Success rate vs number of robots`。
- `Success rate vs injected latency`。
- `Jerk / smoothness`。
- `Collision or safety violation rate`。
- `Recovery latency after disturbance`。
- `Action overwrite / drop rate`。

原因是某些优化会降低 latency，但可能让动作更抖、过期动作更多，或者降低任务成功率。多机器人调度也可能为了提高整体吞吐而牺牲单机器人动作连续性。

### 推荐主指标组合

如果要为多机器人边缘 VLA 推理设计实验，建议至少报告以下指标：

```text
1. TTFA p50 / p95 / p99
2. E2E latency p50 / p95 / p99
3. Goodput under deadline
4. Deadline miss rate
5. Per-robot replanning Hz
6. Action staleness p95 / p99
7. Queueing delay p95 / p99
8. Full chunk latency
9. GPU utilization / memory utilization
10. Task success rate under different robot counts
```

### 对 OpenPI / GR00T 类模型的特别建议

如果模型输出 action chunk，不应只报告 `E2E latency`，而应区分：

```text
TTFA = 第一个动作什么时候能用
Full chunk latency = 整个 chunk 什么时候生成完
TPA = chunk latency / chunk size
Execution horizon = chunk_size / control_frequency
Freshness = 执行动作时观测已经过去多久
```

例如，一个 16-step action chunk 可能完整生成需要 160 ms，摊下来 `TPA = 10 ms/action` 看起来很好；但如果第一个动作也要 160 ms 才能返回，那么动态任务中的反应仍然很慢。

因此，在多机器人共享 GPU 的工厂场景中，核心评价目标应从“GPU 每秒跑多少 request”转为：

```text
在给定机器人数量、控制 deadline 和任务动态性的条件下，系统能稳定交付多少新鲜、及时、可执行的动作。
```
